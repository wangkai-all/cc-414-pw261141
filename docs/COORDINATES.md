# 坐标系统与转换限制（COORDINATES.md）

本项目所有空间计算仅支持一种坐标参考系，限制在此显式声明，避免误用：

## 1. 支持的坐标系

| 项 | 约定 |
|---|---|
| 坐标参考系 | **EPSG:4326（WGS 84 大地基准，经纬度）** |
| 轴顺序 | **(longitude, latitude) / (lon, lat) = (x, y)**，与 GeoJSON RFC 7946 一致 |
| 单位 | 度（degree），不是米 |
| 取值范围 | lon ∈ [-180, 180]，lat ∈ [-90, 90]；入库时强制校验，越界事件被拒绝 |
| GeoJSON `crs` 成员 | **忽略**。RFC 7946 已废弃该成员；上传任何非 EPSG:4326 数据前，调用方必须自行转换 |
| 高度/第三维 | 忽略，只取前两个分量 |

## 2. 计算方式：平面算法，无投影

`pointwise/geometry.py` 的射线法（ray casting）、线段相交、点到线段判定，
全部把经纬度当作笛卡尔平面上的 x/y 直接运算：

* 不做地图投影（不转 Web Mercator / UTM / 高斯-克吕格）；
* 不做大地测量意义上的椭球距离/方位计算；
* 浮点容差 `EPS = 1e-9`（度）仅用于**边线分类的数值抖动**，约等于赤道上
  0.1 mm，**不是地面距离缓冲区**，也不随纬度变化；
* 面积、长度等度量单位因此也是"平方度/度"，项目不输出米制面积。

## 3. 已知几何限制

1. **不处理反子午线（antimeridian，经度 ±180°）穿越**。跨 180° 的多边形必须
   由数据提供方预先切分为两个多边形（MultiPolygon），否则射线法结果错误。
2. **不做极点包裹**，纬度 ±90° 附近的退化多边形未做特殊处理。
3. **不自相交修复**：上传的环若自相交，不会被纠正；区域之间的相交/包含会在
   上传时审计并写入 `validation_notes`，落入重叠区的点得到确定性 `OVERLAP`
   状态，进入冲突流程，而不是被随机分配。
4. **不做坐标转换**：项目不内置也不依赖任何投影库（无 pyproj、shapely、GDAL）。
   若源数据是 EPSG:3857、GCJ-02、BD-09 等，必须在系统外完成转换后再上传；
   GCJ-02/BD-09 等加密坐标与 WGS 84 之间存在系统性偏移，混用会产生百米级归属
   错误。
5. **边界点判定是度空间的精确/近精确判定**：点恰好落在边线上（含浮点抖动
   1e-9 度内）归为 `ON_BOUNDARY`，不会落入任何单一区域，按规则版本处理
   （`MIN_ID` 确定性取最小 region_id，或 `MANUAL` 转人工冲突）。

## 4. 为什么这样取舍

需求只要求真实的**点-面包含**与**聚合**，不做路线规划、缓冲区分析或米制量算。
平面射线法在 EPSG:4326 上的拓扑包含关系（不含上述反子午线等退化情形）与投影
无关——一个点是否在多边形内部是拓扑事实，不随等距投影改变，因此平面算法对
本项目的判定目标是充分的，同时保证零第三方依赖、结果可逐位复现。
